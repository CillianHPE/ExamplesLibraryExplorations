Data collection page archetypes

Five canonical patterns for pages that display collections of data. Start from the user's job, not the component: each card states the job to be done and when the pattern fits or fails. Open an archetype for the full spec and a GreenLake-styled example.

D1 · Archetype

Filterable inventory table

Find and manage these 1,847 things.

The workhorse for operating a known set of objects. Rows are peers; the value is comparing attributes and acting in bulk.

Use when

The collection is large, users know roughly what they want, and rows need comparing or bulk action.

Not when

Users are picking one unfamiliar item by identity, or event order matters more than attributes.

D2 · Archetype

Card grid catalog

Browse and pick one.

For choosing, not managing. Items lead with identity (icon, name, description) so users recognise the right option; the outcome is one selection that starts a flow.

Use when

Items are distinct offerings picked occasionally, and recognition beats attribute comparison.

Not when

Users return daily to operate on many items, or need to scan values across the set.

D3 · Archetype

Faceted event stream

What happened, and when?

For investigating time-ordered records: logs, audit trails, alerts. Users narrow from a symptom; the volume histogram is both overview and zoom control.

Use when

Records are immutable and time-stamped, questions are forensic, and volume is high.

Not when

Users need current state rather than history, or aggregates matter more than single events.

D4 · Archetype

Analytics explorer

What's the trend? Where's the anomaly?

Chart-first: the collection is aggregated before it's shown. One scoped query drives the headline chart and breakdown in sync; rows appear only at the end of a drill-down.

Use when

The question is about patterns over time or across segments, and the honest answer is an aggregate.

Not when

Users need to find and act on specific items: aggregation hides what they're looking for.

D5 · Archetype

Map / spatial view

Where is the problem?

For collections where location is the organising attribute. Map and list share filters and selection; the map is a lens for spotting clusters, never the source of truth.

Use when

"Where" is a question users genuinely ask, and geographic clustering carries meaning.

Not when

Location is just one attribute among many: a filterable column serves better than a map.

Service health widget: what is a row?

The Data Storage overview needs a health widget, and the sketch shows the right shape (status list with 30-day uptime bars) but not yet the right content. Before choosing rows, decide what "health" means for this page. This page walks through the decision, then shows three content options built from the same row anatomy, and closes with a glossary of every monitoring domain a row could represent.

Two different questions hide behind one word

A storage admin opening this page is asking one of two things, and a row means something different for each.

"Is the GreenLake service I depend on working?"

This is service status: the HPE-operated control plane (console, provisioning APIs, backup service, identity). The customer cannot fix any of it; the job is to know quickly whether a problem is theirs or HPE's.

  • A row is one cloud service. Region is a sub-line only where the service is region-scoped.
  • States are status-page vocabulary: Operational, Degraded, Partial outage, Outage, Maintenance.
  • The 30-day uptime bar fits: one segment per day, colour = worst state that day.
  • Rows are stable: the same list every day, in the same order.

"Is my storage estate healthy?"

This is estate health: the arrays, volumes, hosts, replication links and protection jobs the customer owns. They can act on every row, so the widget's job is to point at the exception.

  • A row is one monitored domain (Systems, Volumes, Replication), not one object.
  • Health is a count by status, so the visual is a proportion bar, not an uptime history.
  • The right-hand text is the exception: "2 critical", "14 failed".
  • Critical first: ordering follows severity, not a fixed list.
What the sketch gets tangled on. The current rows mix the two framings and a third axis (region):
  • "Object storage EU-W" and "Identity North America" are cloud services (framing 1), but "Computer Ops EMEA" is neither a data service nor a monitored storage domain.
  • "Data services AUS-NZ" repeated three times treats region as the row, which only works if every row is a region.
  • The footer sentence ("space you never had to buy") is a capacity insight and belongs on the Efficiency card.
  • Each row carries a 30-day bar, but only cloud services have a meaningful daily uptime history; a volume count does not.

Recommendation

Keep the card titled Service health and make it framing 1 (Option A): the neighbouring Capacity and Data protection cards, plus the "Needs your attention" list further down, already cover the estate. If the page has no other estate-health surface, use Option C, which gives service status two rows and spends the rest on the estate.

What each row represents

  • Object storage: S3-compatible object service. Health = API availability and latency SLO per region, so region is named in the sub-line.
  • Data Services console: the management UI and its API. If this is down the customer cannot see or change anything, so it sits second, above the data planes.
  • Block storage: provisioning, host mapping and management for arrays. The arrays keep serving I/O when this is degraded; the row is about being able to manage them.
  • File storage: the file service control plane.
  • Backup and recovery: cloud backup targets and scheduling. Degraded here means protection jobs are at risk, which is why Data protection sits beside this card.
  • Disaster recovery: continuous replication and orchestration.
  • Identity and access: sign-in, SSO federation, RBAC. Amber on days 13 and 14 shows a maintenance window.

Rules encoded

Ordering is worst-first, then a fixed canonical order for the operational rows so the list is scannable day to day. The sub-line explains the state ("degraded since 09:12 UTC") only when the state is not Operational. The footer is the one open incident and a link to history; if there are no incidents the footer is omitted.

Bar: 30 segments, one per day, newest on the right. Colour = worst state during that day. Hover gives the date and duration; the bar never encodes a percentage.

What each row represents

  • Systems: the arrays themselves. Health from hardware telemetry: controllers, drive sets, power, fans, temperature. Critical = redundancy lost.
  • Volumes: logical volumes served to hosts. Warning = offline, over capacity threshold, or breaching a latency SLO.
  • Host connectivity: initiators and paths. Warning = single-path host; critical = host with no active path.
  • Replication: partnerships between systems. Warning = link lagging its RPO; critical = link down.
  • Protection jobs: snapshots and backups in the last 24 hours. Red = failed runs. This overlaps the Data protection card, which shows coverage; this row shows execution.
  • Firmware baseline: systems not on the recommended release. Never critical on its own; a warning that feeds risk.

Rules encoded

Rows sort critical first, then warning, then healthy. The proportion bar shows counts, so a domain with 1,842 items and 33 warnings still reads mostly green; the right-hand text carries the exception so the eye does not have to judge a sliver. The card is titled Storage health because it is about the estate, not the service.

Because rows are counts, not histories, there is no 30-day bar. If a trend is wanted, it belongs on a drill-down, not in the list.

How it reads

Top to bottom follows the dependency chain: if the service layer is degraded, that is often the cause of the rows beneath it, which is exactly the story in this example (a degraded object target causing failed backup jobs). The footer sentence makes that link explicit rather than leaving the admin to join the dots.

  • Service keeps the uptime-bar treatment because it has a daily history. Operational services collapse into one row ("5 other services") so the group never exceeds two or three rows.
  • Infrastructure and Data use the proportion treatment from Option B. Sub-lines shrink to the count only; the domain name carries the meaning.
  • Group labels are the small-caps row style already used in "Needs your attention".

Trade-offs

Two visual encodings in one card costs some scan speed, and the card is taller (seven rows plus three group labels). It earns its place only when it replaces two cards, not when it sits beside them.

Title becomes plain Health because neither "Service" nor "Storage" describes the whole.
